# DDD コードレビュー

DDD の戦術的パターン（+ 必要に応じて戦略的パターン）を検査軸としてコードをレビューし、**「不変条件が破れる・モデルが劣化する・変更が波及する」具体的なシナリオに紐づく指摘だけ**を報告する。パターンの形をなぞっていないだけで実害のシナリオが書けないものは指摘しない（→「過剰適用を避ける」）。

## レビュー対象の決定

1. **引数でファイル・ディレクトリ・PR番号が指定されたら**それを対象にする
2. **指定がなければ working tree の差分**（`git diff HEAD`、なければ `git diff main...HEAD`）を対象にする
3. 差分だけでは判断できない場合は必ず**周辺コードも読む**。DDD 違反は1ファイルでは判定できないことが多い（集約境界は複数エンティティ、不変条件の破壊は setter の呼び出し元、コンテキスト混線は import 関係を見る必要がある）
4. **そのプロジェクトが DDD を採用しているかをまず確認する**。ディレクトリ構成（`domain/` の有無）、CLAUDE.md・アーキテクチャドキュメント、既存コードの書き方から判断する。DDD を採用していない CRUD アプリに DDD の語彙で指摘しない — その場合はレビュー冒頭でその旨を伝え、明らかな実害（不変条件がどこでも守られていない等）だけ一般的な設計指摘として報告する

対象言語は問わない。クラスのない言語（Go 等）では「エンティティ」を「struct + メソッド群」、「集約」を「パッケージ内の型グループ」と読み替えて適用する。

## レビュー手順

1. 対象コードと周辺（呼び出し元・集約内の他エンティティ・import 関係）を読む
2. 下記の検査軸に沿って走査する
3. 各候補について**「どんな操作・変更が来たとき、どの不変条件が破れる / 何が壊れる / 何箇所直すことになるか」**を1文で書けるか自問する。書けなければ捨てる
4. 残った指摘を重要度順に報告する（フォーマットは末尾）

## 1. ユビキタス言語 — 名前がドメインを語っているか

> コードの語彙はドメインエキスパートの語彙と一致すべき。翻訳が必要な名前は、仕様とコードの乖離を生む。

**検出シグナル:**

- 同じ概念に複数の名前がある（`Customer` / `Client` / `User` が同じものを指して混在。仕様書の用語とコードの用語が食い違う）
- ドメイン概念が**汎用語に溶けている**（`data` / `info` / `item` / `record` / `process()` / `handle()` — 業務ルールを実装しているのに名前から業務が読み取れない）
- ドメインの区別がコードで潰れている（業務上「見積もり」と「注文」は別概念なのに、1つの `Order` に `isEstimate` フラグで同居）
- boolean / enum / int の組で状態を表し、業務上の状態名（「承認待ち」「差し戻し」）がコードに存在しない

**指摘しないもの:** インフラ・技術層の汎用名（`Repository` の `Save`、HTTP ハンドラの `Handle`）。ドメイン層の外は技術の語彙で正しい。

**修正の方向:** ドメインエキスパートが使う語に改名する。フラグ同居は型を分けるか、状態を明示的な enum / 状態オブジェクトにする。

## 2. 貧血ドメインモデル — ロジックがモデルの外に漏れていないか

> エンティティ・値オブジェクトは自分のデータに関するルールを自分で守る。getter/setter だけの構造体 + 外部のロジックは DDD ではなくデータ指向設計。

**検出シグナル:**

- エンティティが **public フィールド / getter・setter のみ**で、業務ルール（状態遷移の可否、計算、検証）が全部サービス層に書かれている
- **同じ判定ロジックがサービス層の複数箇所に重複**している（`if order.Status == "paid" && !order.Shipped` のような判定が N 箇所 — エンティティにメソッドがないから呼び出し側が毎回組み立てる）
- 状態遷移が外から setter で直接行われる（`order.SetStatus(Cancelled)` — キャンセル可能条件のチェックが呼び出し側任せで、チェックを忘れた呼び出し箇所から不正遷移が入る）
- エンティティのフィールドを取り出して計算し、結果を書き戻すコードがサービス層にある（Tell, Don't Ask 違反: `total := calcTotal(order.Items); order.Total = total`）

**指摘しないもの:** DTO・リクエスト/レスポンス型・DB モデル（これらはデータ運搬役であり貧血で正しい）。CRUD しかない画面設定のような、守るべきルールが本当に存在しないモデル。

**修正の方向:** 判定・計算・状態遷移をエンティティのメソッドに移す（`order.Cancel()` が可否判定と遷移を両方持つ）。setter を廃し、意図を表すメソッド（`Approve()` / `Reject(reason)`）に置き換える。

## 3. 値オブジェクト — プリミティブがドメイン概念を運んでいないか

> 金額・メールアドレス・期間などの概念は、検証と演算を持つ不変の型にする。

**検出シグナル:**

- **同じプリミティブへの同じバリデーションが複数箇所に散在**（メール形式チェックが登録・変更・インポートの3箇所にコピペ — 値オブジェクトのコンストラクタなら1箇所）
- 単位・通貨・タイムゾーンの取り違えが**型で防げていない**（`amount float64, currency string` を別々に引き回す。`func Transfer(from, to string)` — 口座IDを2つ渡す順番を間違えてもコンパイルが通る）
- 生成後に変更可能な「値」（`Money` の `Amount` フィールドが public で書き換え可能 — 共有参照経由で他所の値が変わる事故が起きうる）
- 業務的な演算がユーティリティ関数に散っている（`AddMoney(a, b float64)` — `Money.Add(other Money)` なら通貨不一致をその場で検出できる）

**指摘しないもの:** 一度しか使わないプリミティブの全部を型に包む要求。検証・演算・取り違えリスクのどれも無い値は string / int のままでよい。

**修正の方向:** コンストラクタ（ファクトリ関数）で検証し、不正な値のインスタンスが**存在できない**型を作る。不変にし、演算は新しい値を返す。

## 4. 集約 — 不変条件とトランザクション境界が守られているか

> 集約は「常に一貫していなければならないデータの塊」の単位。1トランザクション = 1集約の更新が原則。集約ルート経由でのみ内部を変更する。

**検出シグナル:**

- **集約内部のエンティティが外から直接変更されている**（`order.Items[0].Quantity = 99` や `order.GetItems().Add(item)` — ルートの `order.AddItem()` を経由しないため「合計金額 = 明細の和」「明細は10件まで」等の不変条件チェックが素通りする）— 最重要シグナル
- 内部コレクションを可変のまま返している（`GetItems() []*Item` が内部スライスをそのまま返す — 呼び出し側が自由に書き換えられる）
- **1トランザクションで複数の集約を更新**している（注文確定と在庫引当を同一 Tx で複数集約に書き込む — 集約境界が広すぎるか、結果整合（ドメインイベント等）にすべき箇所）
- 集約が**別の集約をオブジェクト参照で保持**している（`Order` が `*Customer` を丸ごと持つ — ID 参照 `CustomerID` なら防げる、巨大な読み込み連鎖と更新競合の温床）
- 不変条件がリポジトリや DB 制約にしか存在しない（アプリ内では不正な中間状態が作れてしまい、保存時に初めて失敗する）
- 集約が巨大でロック競合・全件ロードが問題になっている（1つの `Company` 集約が全社員を内包し、社員1人の更新で全体を読み書き）

**指摘しないもの:** 読み取り専用のクエリが複数集約をまたぐこと（CQRS 的に読みモデルは自由でよい）。ID 参照で複数集約を「参照」すること（更新でなければ問題ない）。

**修正の方向:** 変更操作を集約ルートのメソッドに集約し、不変条件チェックをそこに置く。コレクションはコピーか読み取り専用ビューで返す。集約間はID参照 + 結果整合にする。不変条件を共有しないなら集約を分割する。

## 5. リポジトリ — 集約単位・ドメインの語彙になっているか

> リポジトリは集約ルート単位で、ドメインの言葉でコレクション操作を提供する。DB の都合を漏らさない。

**検出シグナル:**

- **集約ルートでないエンティティ専用のリポジトリ**がある（`OrderItemRepository` — 明細を単独で保存できるため、集約ルート経由の不変条件チェックを迂回する裏口になる）
- リポジトリのインターフェースに **DB・ORM の型や語彙が露出**している（戻り値が GORM モデル、引数に `*sql.Tx`、メソッド名が `SelectByQuery(where string)`）。ドメイン層がインフラに引っ張られる
- 集約の**一部だけを保存するメソッド**がある（`UpdateOrderStatus(id, status)` — 集約全体の一貫性を保った保存にならず、不変条件の破れた部分更新が可能）
- ドメイン層にクエリビルダ・SQL 断片が漏れている

**指摘しないもの:** パフォーマンスのための読み取り専用クエリサービス（検索画面用の DTO 返却など）を別に持つこと。インフラ層の実装内部が ORM に依存すること（それが仕事）。

**修正の方向:** リポジトリは集約ルート単位に統一し、`Save(order)` が集約全体を永続化する形にする。インターフェースはドメイン層に置き、ドメインの型だけで定義する。

## 6. ドメイン層の純粋性 — 技術的関心が漏れ込んでいないか

> ドメイン層は業務ルールだけを持つ。フレームワーク・DB・外部APIの知識が入ると、ルールの見通しとテスト容易性が失われる。

**検出シグナル:**

- ドメイン層（エンティティ・値オブジェクト・ドメインサービス）が**インフラを import** している（エンティティに ORM タグ + DB フック、ドメインサービスが HTTP クライアントを直接呼ぶ）
- エンティティが**永続化モデルと兼用**されている（DB スキーマ変更のたびにドメインモデルが引きずられる。逆も然り）
- ドメインロジックの中に技術的分岐（リトライ、キャッシュ、トランザクション制御）が混ざっている
- ドメイン層のテストに DB・モックサーバが必要（純粋ならインメモリで完結するはず）

**指摘しないもの:** 小規模プロジェクトでエンティティと DB モデルを意図的に兼用する判断（プロジェクト規約として明示されているなら従う。ただし不変条件が ORM の都合で守れなくなっている場合は指摘する）。標準ライブラリへの依存。

**修正の方向:** 永続化モデルを分離しマッピングで変換する。外部呼び出しはドメイン層にインターフェース（ポート）を定義してインフラ層に実装させる。

## 7. サービスの責務配置 — ドメインサービスとアプリケーションサービスの混同

> ドメインサービス = 複数の集約・エンティティにまたがる**業務ルール**。アプリケーションサービス（ユースケース）= 手順のオーケストレーション（取得→ドメイン操作→保存→通知）。

**検出シグナル:**

- アプリケーションサービス（ユースケース層）に**業務ルールの本体**が書かれている（割引率の計算、承認可否の判定が usecase 関数にベタ書き — 別のユースケースから同じルールが必要になったときコピペされる）
- 1エンティティで完結するロジックがドメインサービスに置かれている（`OrderService.CalcTotal(order)` — `order.CalcTotal()` でよい。エンティティが貧血化する引力になる）
- ドメインサービスがリポジトリ以外のインフラ操作・トランザクション制御まで持っている（それはアプリケーションサービスの仕事）
- 「とりあえず Service に置く」で肥大した `XxxService` が変更理由の異なるルールを多数抱えている

**指摘しないもの:** 取得→変更→保存だけの薄いユースケース（それがあるべき姿）。真に複数集約にまたがるルール（口座間送金、重複チェック）をドメインサービスに置くこと（それが正しい置き場所）。

**修正の方向:** ルールは第一候補としてエンティティ / 値オブジェクトへ、複数集約にまたがる場合のみドメインサービスへ。ユースケースは手順書の読みやすさだけを責務にする。

## 8. 境界づけられたコンテキスト — モデルの混線（戦略的パターン）

> モデルはコンテキストの中でのみ一貫した意味を持つ。コンテキストをまたいでモデルを共有すると、両方の変更理由を背負い込む。

**検出シグナル:**

- 別コンテキスト（別モジュール・別サービス・別チーム管轄）のドメインモデルを**直接 import して自分のロジックに使っている**（販売コンテキストが在庫コンテキストの `StockItem` エンティティを直接操作 — 在庫側のモデル変更が販売側を壊す）
- 1つの「神モデル」が全コンテキストで共有されている（`User` が認証・課金・配送の全属性を持ち、どの機能の変更でも `User` が変更される）
- 外部システム・他コンテキストのレスポンス型がドメイン層まで貫通している（腐敗防止層がなく、外部 API の仕様変更がドメインロジックの修正を強制する）

**指摘しないもの:** モジュラーモノリス内で ID や共有カーネルとして合意された最小限の型を共有すること。差分レビューでコンテキスト地図全体を再設計する提案（境界の再編は差分レビューのスコープ外 — 差分が混線を**新たに持ち込む/悪化させる**場合のみ指摘する）。

**修正の方向:** コンテキスト境界では自分のモデルに変換する（腐敗防止層 / 変換アダプタ）。他コンテキストへは公開契約（API・イベント）経由でアクセスする。

## 過剰適用を避ける（指摘の足切り基準）

DDD は「複雑なドメインのモデルを保守可能に保つ」ための手段であり、パターン適用自体が目的ではない。以下は**指摘しない**:

- **実害シナリオが書けない違反**。すべての指摘は「◯◯の操作/変更が来たとき、△△の不変条件が破れる / △△が壊れる / N箇所の修正が必要になる」の形で書けること。「DDD 的にはこうすべき」だけの指摘は出さない
- **複雑さのないドメインへの戦術パターン強要**。単純な CRUD・設定画面・管理ツールに集約やドメインサービスを要求しない。守るべき不変条件が存在しないなら貧血モデルで正しい
- **差分の外にある既存構造の全面改修**。既存の問題は差分がそれを**悪化**させる場合のみ言及する
- **語彙・レイヤー規約はプロジェクト優先**。適用先に既存のアーキテクチャガイド（例: go-clean-architecture 規約、ORM モデル兼用の明示的判断）がある場合はそちらの境界定義・妥協を尊重し、その規約の中で守れるはずの不変条件が破れている点だけを指摘する

## 報告フォーマット

指摘は重要度順に並べる。件数を稼がない — 0件なら「DDD 観点の指摘なし」と明言し、確認した観点を1行で添える。

各指摘は以下の形式:

```
### [重要度] 観点 — 一言サマリ

- 場所: path/to/file.go:42
- 問題: どの観点にどう反しているか（1〜2文）
- 実害シナリオ: 「◯◯の操作/変更が来たとき、△△が破れる/壊れる/N箇所の修正が必要になる」
- 修正案: 方向性 + 必要なら最小のコード例
```

重要度の基準:

| 重要度 | 基準 |
|---|---|
| High | 不変条件が実際に破れる経路が存在する（集約迂回の直接変更、部分更新リポジトリ、検証なしで生成できる値）、複数集約の同一Tx更新による整合性リスク |
| Medium | 今は壊れないが変更コスト・事故率を確実に上げている（判定ロジックのサービス層重複、ドメイン層へのインフラ漏れ、コンテキスト間のモデル直結） |
| Low | 繰り返すと構造問題になる兆候（汎用語への語彙の溶解、フラグによる概念同居、Service の肥大傾向） |

修正の適用はユーザーが求めた場合のみ行う。レビュー依頼に対しては報告で止める。
