## 検査軸

1. **ユビキタス言語** — 作業ブリーフ・ドメインの用語とコードの名前が一致しているか。
   汎用語（data / info / process）にドメイン概念が溶けていないか
2. **貧血モデル** — 業務ルール（判定・計算・状態遷移）がエンティティの外
   （ユースケース層）に漏れていないか。setter で状態を外から変えていないか
3. **値オブジェクト** — 検証・演算・取り違えリスクのあるプリミティブが型に
   なっているか
4. **集約** — 集約ルートを迂回した内部変更がないか。1トランザクションで複数集約を
   更新していないか。**作業ブリーフの「守るべき不変条件」が破れる経路がないか**（最重要）
5. **リポジトリ** — 集約単位か。部分更新メソッドや DB の語彙の露出がないか
6. **ドメイン層の純粋性** — インフラ（ORM・HTTP・フレームワーク）がドメイン層に
   漏れ込んでいないか
7. **サービスの責務** — 業務ルールがユースケース層にベタ書きされていないか

## 足切り基準（重要）

- すべての指摘は**「◯◯の操作/変更が来たとき、△△の不変条件が破れる / △△が壊れる /
  N箇所の修正が必要になる」の実害シナリオ形式**で書けること。書けない指摘は捨てる
- 「DDD 的にはこうすべき」だけの形式論・差分の外にある既存構造の全面改修は指摘しない
- プロジェクト規約（作業ブリーフ記載）が意図的な妥協をしている場合はそれを尊重する
- 件数を稼がない。0件なら「指摘なし」と明言する

## Constraints

- ファイルの変更・作成・git 操作（読み取り系の log / diff / show を除く）をしない

## Output contract

最終メッセージに以下の見出しを必ず含める:

- `## Findings` — 指摘の一覧（重要度順）。各指摘は以下の形式:
  ```
  ### [High|Medium|Low] 観点 — 一言サマリ
  - 場所: path/to/file:42
  - 問題: どの観点にどう反しているか（1〜2文）
  - 実害シナリオ: 「◯◯が来たとき△△が破れる」
  - 修正の方向: 1〜2文
  ```
  High = 不変条件が実際に破れる経路がある / Medium = 変更コスト・事故率を確実に
  上げている / Low = 兆候レベル。指摘なしなら "none" と確認した観点を1行
- `## Verdict` — `pass`（High / Medium なし）か `needs-work`（High / Medium あり）
