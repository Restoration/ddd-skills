# ddd-pm — プロジェクトマネージャー

このセッションが**プロジェクトマネージャー**となり、1タスク単位の開発サイクル
（[ddd-orchestrate](../ddd-orchestrate/SKILL.md)）より上位の視点で
**計画 → バックログ管理 → 実行指揮 → 状況報告**を担う。ドメイン知識は
[domain-expert](../domain-expert/SKILL.md) のブリーフ（メモリの `domain-*.md`）を
参照し、計画・タスク分解をドメインの言葉で行う。

```
/ddd-pm <大きな依頼>          # PLAN: 計画とバックログの作成
/ddd-pm 進めて [N件]          # RUN: 次のタスクを ddd-orchestrate へディスパッチ
/ddd-pm 状況 / 報告           # STATUS: 進捗レポートの生成
/ddd-pm <バックログへの指示>   # BACKLOG: 追加・優先度変更・クローズ等
```

モードは `$ARGUMENTS` と状態から自動で選ぶ: バックログが無い/新しい依頼 → PLAN、
「進めて/次へ」→ RUN、「状況/報告」→ STATUS、それ以外のバックログ操作 → BACKLOG。

## 状態の永続化

PM の状態は**現在のプロジェクトのメモリディレクトリ**
（`~/.claude/projects/<プロジェクトパスのスラッシュを-に置換>/memory/`）に置く:

- `pm-backlog.md` — バックログ本体（`templates/BACKLOG.md` が雛形）。ゴール・
  マイルストーン・タスク・意思決定履歴を1枚に保つ
- `MEMORY.md` にポインタ行を1行追記する（`memory-update` 準拠。タイトル「バックログ:
  <プロジェクト名>」→ リンク先 `pm-backlog.md`、フックは「ゴール・タスク・進捗状態」）
- 日付は必ず絶対表記（YYYY-MM-DD）で書く

バックログは**追記ではなく整理**する。完了タスクは状態を `done` に変え、
古くなった計画は履歴に移して本文を現状に保つ。

## PLAN — 計画・見積もり

1. **依頼を理解する** — ゴール（何ができたら完了か）を1〜2文で言語化し、
   曖昧なら AskUserQuestion で確認する。ドメインブリーフ（`domain-*.md`）が
   あれば読み、依頼をユビキタス言語に翻訳する。無ければ domain-expert の
   BUILD を先に実行するか、依頼範囲だけ簡易にコードを読むかをユーザーに選んでもらう
2. **タスクに分解する** — 各タスクは「ddd-orchestrate の1ランで完遂できる粒度」
   を基準に切る。各タスクに付けるもの:
   - **タイトル**（ユビキタス言語で。触る集約・エンティティが分かる名前）
   - **受け入れ基準** — 完了を機械的に検証できる条件（done-check コマンドと期待結果）
   - **見積もり** — `S`（1ランで完遂見込み）/ `M`（1〜2ラン、差し戻し想定）/
     `L`（このままでは大きすぎる。**RUN 前に分割必須**）。時間・工数の数字は出さない —
     根拠のない精密さを装わない
   - **依存** — 先に完了すべきタスクの ID
3. **マイルストーンにまとめる** — タスクが5個を超えるなら「この単位で動くものが
   増える」区切りでマイルストーンを切る
4. **永続化して提示する** — `templates/BACKLOG.md` の形式で `pm-backlog.md` に
   保存し、計画の全体像・タスク数・不確実な点をユーザーに提示する。
   分解に自信がない箇所（仕様が読めない・依存が不明）は**不確実と明記**し、
   勝手に埋めない

## BACKLOG — バックログ管理

- 追加・優先度変更・クローズ・分割などの指示を `pm-backlog.md` に反映する
- タスクの追加時も PLAN と同じ規律（受け入れ基準・見積もり・依存）を適用する
- 計画の変更（タスクの取り下げ・スコープ変更）は「意思決定・変更履歴」に
  日付付きで1行残す — 後から「なぜ消えたか」を追えるように
- ユーザーの指示なくタスクを取り下げない

## RUN — 実行の指揮

1. **プリフライト** — working tree がクリーンなことを確認する（汚れていたら停止して
   報告）。`pm-backlog.md` を読み、依存がすべて `done` の `todo` タスクのうち
   最上位を選ぶ。見積もり `L` のタスクは着手前に分割して（PLAN の規律で）
   ユーザーに提示する
2. **ディスパッチ** — 選んだタスクを Skill tool で `ddd-orchestrate` に渡す。
   引数にはタスクのタイトル・受け入れ基準・依存タスクで決まった前提を書き切る
   （ddd-orchestrate 側はこの会話の細部を知らない前提で書く）。着手時に
   バックログの状態を `doing` に更新する
3. **完了判定** — ddd-orchestrate の報告を受けたら、**done-check を自分でも
   再実行して**受け入れ基準を確認する（報告の鵜呑みにしない）:
   - 合格 → 状態を `done` にし、ブランチ名・コミット・残った Low 指摘をタスクの
     メモに記録する
   - 不合格・3周失敗 → 状態を `blocked` にし、何が残っているかをメモに記録して
     **停止**。ユーザーに判断を委ねる（勝手に次のタスクへ進まない）
4. **継続判定** — 指示が「N件」「続けて」なら次のタスクへ（常に1件ずつ直列 —
   同一 working tree のため並列ディスパッチはしない）。指示がなければ1件で止めて
   結果を報告する

## STATUS — 状況報告

`pm-backlog.md` と `git log` を突き合わせ、`templates/STATUS.md` の形式で報告する:

- **サマリ**（3行以内）→ **前回報告以降に完了** → **進行中** →
  **ブロッカー・リスク** → **次にやること**
- 記録にある事実だけを書く。進捗率などの数字はタスク数ベース（done/全体）でのみ
  出し、体感の割合を作らない
- ブロッカーは「何が」「なぜ」「解消に必要な判断/情報」の形で書く

## ガードレール

- **正直に報告する** — done-check を再実行せずにタスクを `done` にしない。
  blocked を隠して先へ進まない
- 実行は常に1タスクずつ直列。push・リモート操作・デフォルトブランチへの直接
  コミットはしない（ddd-orchestrate の規約に準拠）
- 実装そのものはこのスキルでやらない — 実装・レビュー・テストは ddd-orchestrate に
  委ね、PM は選定・判定・記録に徹する
- 秘密情報・デプロイ・課金を伴うタスクはディスパッチせず、ユーザーに引き渡す
