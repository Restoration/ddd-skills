# ドメインモデリング

要件から**これから作るドメインモデル（to-be）**を設計する。[domain-expert](../domain-expert/SKILL.md) が「既にあるコード・仕様からの抽出（as-is）」を担うのに対し、このスキルは「まだ存在しないモデルの設計」を担う。成果物は domain-expert と同じメモリ形式で永続化するため、[ddd-pm](../ddd-pm/SKILL.md) / [ddd-orchestrate](../ddd-orchestrate/SKILL.md) がそのまま作業ブリーフの材料として読める。

モードは2つ。既存の状態から自動で選ぶ:

- **DESIGN（新規モデリング）** — 新規プロジェクト、または既存モデルと独立した新しいコンテキストの設計。保存済みブリーフ（`domain-*.md`）も該当ドメインの実装もないとき
- **EXTEND（追加設計）** — 既存のモデル（保存済みブリーフ or 実装）の上に新機能分の設計を積むとき

## メモリの場所（domain-expert 互換）

設計成果は**現在のプロジェクトのメモリディレクトリ**に永続化する:

```
~/.claude/projects/<プロジェクトパスの / や . 等の記号を - に置換>/memory/
```

- ファイルは `domain-<area>.md`（コンテキストごと。小規模なら `domain-brief.md` 1枚）。frontmatter は domain-expert と同一:

```markdown
---
name: domain-<area>
description: <このファイルが何のドメイン知識か。recall のヒットに使われる一文>
metadata:
  type: reference
---
```

- **本文冒頭に設計ステータス行を置く**（as-is の抽出結果と区別するため）:

```markdown
> 設計（to-be・未実装）: YYYY-MM-DD 設計。実装が進んだら domain-expert の REFRESH で実装と突き合わせて統合する。
```

- `MEMORY.md` にポインタ行を1行追記する（`- タイトルへのリンク — フック` の形。例: 「ドメイン設計: 注文」→ `domain-order.md`、フックは「注文集約の設計・不変条件（未実装）」）
- 日付は絶対表記（YYYY-MM-DD）で書く

## DESIGN — 新規モデリング

### 1. 要件を集める

まず手元にある材料を読む: 要件文書・企画メモ・issue・README・ユーザーが会話で述べた要望。

足りない部分は AskUserQuestion で**ヒアリング**する。聞き方はイベントストーミングの順序に従い、**業務の言葉で聞く**（ユーザーに DDD 用語を要求しない）:

1. **ドメインイベント** — 「この業務で起きる出来事を、起きた順に教えてください（例: 注文が確定した、支払いが完了した）」。過去形で列挙してもらう
2. **コマンドとアクター** — 各イベントについて「誰（またはどのシステム・どんな時間経過）の、どんな操作で起きますか」
3. **ルールと不変条件** — 「その操作が許されない・失敗すべきなのはどんなときですか」「常に成り立っていなければならない計算・制約はありますか」
4. **照会** — 「業務の判断のために見たい情報・一覧はありますか」（読みモデル候補。集約設計に押し込まない）

一度に全部を聞き切ろうとしない。**核となるユースケース1〜2本**から始め、モデルを仮組みしてから広げる。回答が曖昧な箇所は追加で聞くか、「前提・未解決の疑問」に残す。

### 2. モデルを設計する

以下の軸で組み立てる。**各設計判断に理由を1文付け、迷った箇所は検討した代替案も残す**:

1. **ユビキタス言語（用語集）** — ヒアリングで出た業務語をそのまま用語にする。同義語・表記ゆれは1語に正規化する（どれを正とするかはユーザーに確認）
2. **集約** — コマンドと不変条件をグルーピングし、「**1トランザクションで一貫していなければならない最小の塊**」を集約の単位にする。各集約に: ルート / 内部のエンティティ・値オブジェクト / 守る不変条件 / 受けるコマンド / 発するイベント。設計段階から [ddd-review](../ddd-review/SKILL.md) の検査軸を満たす形にする（集約間は ID 参照、1Tx1集約、内部変更はルート経由、可変コレクションを露出しない）
3. **値オブジェクト** — 検証・演算・取り違えリスクを持つ値（金額・期間・識別子の組など）を型として切り出す。リスクのないプリミティブは無理に包まない
4. **ワークフロー** — 主要ユースケースを「コマンド → 集約のメソッド → イベント →（後続があれば）次のコマンド」の連鎖で書く
5. **コンテキスト境界** — 同じ語が別の意味になる箇所、責務・チーム・変更理由が切り替わる箇所で境界を引く。境界間の連携方式（イベント / API / 腐敗防止層）を決める。コンテキストが1つで足りるならそれを明記して終わる
6. **前提・未解決の疑問** — ヒアリングで確定しなかった点・推測で置いた点を**明示的にリスト化**する。勝手に埋めないことが誠実さ

### 3. モデルを検証する（ウォークスルー）

永続化の前に、主要ユースケースを机上でなぞって設計を検証する:

- 各ユースケースについて「コマンド → どの集約のどのメソッドが受ける → どの不変条件をどこでチェック → 何のイベントを発する」が淀みなく書けるか
- **赤信号**（出たら境界を引き直す）: 1ユースケースが複数集約の同一トランザクション更新を要求する / 不変条件の置き場所となる集約がない / 1つの集約がほとんどのユースケースに登場して肥大している / 用語集の同じ語が場所によって別の意味で使われている
- ウォークスルーで見つけた不整合は設計を直すか、直せない理由と共に「前提・未解決の疑問」へ

### 4. 永続化と報告

- 「2. モデルを設計する」の全軸を `domain-<area>.md` に保存する（冒頭に設計ステータス行、frontmatter、`MEMORY.md` ポインタ — 上記「メモリの場所」参照）
- 報告する:
  - 設計の要約（コンテキスト・集約・主要な不変条件の一覧。構造が伝わりにくければ mermaid 図を添える）
  - 主要な設計判断とその理由（なぜこの集約境界か）
  - **「前提・未解決の疑問」を筆頭に提示**し、ユーザーに確認する
  - 次工程の案内 — 計画に進むなら `/ddd-pm <依頼>`、直接実装に進むなら `/ddd-orchestrate <タスク>`（どちらも保存したブリーフを読んで動く）

## EXTEND — 追加設計

1. **既存の文脈を読む** — 保存済みブリーフ（`domain-*.md`）と、関連するドメイン層の実装を読む。ブリーフが無く実装だけがある場合は、domain-expert の BUILD を先に実行するか、対象範囲だけ簡易にコードを読むかをユーザーに選んでもらう
2. **新要件を既存の言語に翻訳する** — 新しく出てきた概念が既存の用語と同じものか別物かを確認する（同じ語で意味が違うならコンテキスト境界のサイン。安易に既存の語を流用しない）
3. **差分を設計する** — 新しい振る舞いが「既存集約のメソッド追加で守れるか / 新しい集約が要るか / 境界の変更まで要るか」を判断する。設計の規律は DESIGN の 2〜3 と同じ（ウォークスルーまで行う）。既存モデルとの整合が崩れる場合（既存の不変条件と矛盾する要件など）は、勝手に既存側を変えず矛盾としてユーザーに提示する
4. **既存ファイルを更新する** — 新設 `domain-*.md` の乱造ではなく、対応する既存ファイルに設計差分を統合する。新設計の部分には「（設計・未実装 YYYY-MM-DD）」の印を付け、as-is の記述と区別できるようにする

## 過剰設計を避ける

DDD は複雑なドメインのための手段であり、モデリング自体が目的ではない:

- **ドメインが薄いなら薄いと言う**。CRUD 中心で守るべき不変条件がほとんどないなら、集約・コンテキストの設計を強要せず「このドメインは薄く、主なルールは X のみ」で止める
- **今の要件で必要な複雑さだけをモデルにする**。想像上の将来要件のために境界・抽象を先回りして切らない
- 精緻な図や網羅的な用語集より、**不変条件と集約境界の明確さ**を優先する

## ガードレール

- **コードは書かない**。成果物はメモリファイルと報告のみ。実装は software-engineer / ddd-orchestrate の領分（スキャフォールドも書かない）
- 不明点を推測で埋めない。推測は推測と明示し、「前提・未解決の疑問」に集約する
- ヒアリングは業務の言葉で行い、モデルへの翻訳はこちらの仕事にする
- 既存の as-is 記述（domain-expert の抽出結果）を設計で上書きしない。to-be は未実装マークで区別し、統合は実装後の domain-expert REFRESH に委ねる
