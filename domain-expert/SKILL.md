# ドメインエキスパート

プロジェクトの**仕様（何を作るべきか）と実装（実際に何をしているか）**を読み込み、ドメイン知識を構造化してメモリに永続化する。以後は保存済みのブリーフに**厳密に根拠づけて**質問に答える。推測は推測と明示し、根拠がなければ「不明」と言う。

このスキルは3つのモードで動く。`$ARGUMENTS` と現在の状態から自動で選ぶ:

- **BUILD**（取り込み）— まだブリーフがない、または「ドメインを取り込んで/学んで」と言われたとき。仕様と実装を探索して抽出・永続化する
- **ASK**（応答）— ドメインに関する質問が来たとき。保存済みブリーフを読み、根拠づけて答える
- **REFRESH**（更新）— コードが変わった、「ドメイン知識を更新して」と言われたとき。既存ブリーフと現状の差分を取り、変わった箇所だけ更新する

## メモリの場所

ドメイン知識は**現在のプロジェクトのメモリディレクトリ**に永続化する:

```
~/.claude/projects/<プロジェクトパスの / や . 等の記号を - に置換>/memory/
```

（例: `/home/user/Repos/foo` → `~/.claude/projects/-home-user-Repos-foo/memory/`）

- ディレクトリがなければ作る（`mkdir -p`）
- ドメインファイルは `domain-<area>.md`（コンテキストごと。小規模なら `domain-brief.md` 1枚）
- 各ファイルは下記のメモリ frontmatter を付ける（`description` が recall のヒットに使われるので中身を語る一文にする）
- `MEMORY.md` にポインタ行を1行追記する（`memory-update` 準拠。`- タイトルへのリンク — フック` の形。例: 「ドメイン: 注文」→ `domain-order.md`、フックは「注文集約の状態遷移と不変条件」）

メモリファイルの frontmatter:

```markdown
---
name: domain-<area>
description: <このファイルが何のドメイン知識か。recall のヒットに使われる一文>
metadata:
  type: reference
---
```

## BUILD — ドメインの取り込み

### 1. 知識ソースを洗い出す

仕様側と実装側の**両方**を集める。片方だけでは「あるべき姿」と「現状」の乖離が見えない。

- **仕様側**: `README`・`docs/`・`ADR`/`adr/`・`*.md` 設計文書・OpenAPI/Swagger・`*.proto`・GraphQL schema・`CLAUDE.md`・課題管理へのリンク・コード内の doc コメント
- **実装側**: ドメイン層（`domain/`・`model/`・`entity/`・`core/`）、中核ビジネスロジック（状態遷移・計算・検証）、DB スキーマ/マイグレーション、enum・定数、バリデーション

探索が広い場合は **Explore サブエージェントに並行ファンアウト**させる（例: 「仕様文書を洗い出して要点を抽出」「ドメイン層のエンティティと不変条件を抽出」「状態遷移とワークフローを抽出」を別エージェントに）。各エージェントには**引用（file:line）付きで返す**よう指示する。

### 2. ドメイン知識を抽出する

以下の軸で構造化する。**各項目に根拠（file:line）を必ず付ける**。根拠が仕様にしかない/実装にしかない場合はそれも明記する（乖離のサイン）。

1. **ユビキタス言語（用語集）** — ドメインの中核概念と定義。コードでの名前 ↔ 業務用語の対応。同義語・表記ゆれ（`Customer`/`Client`/`User` の混在など）も記録
2. **中核エンティティと関係** — 主要な型、識別子、所有/参照関係、集約境界（どの単位で整合性が保たれるか）
3. **ビジネスルール・不変条件** — 「常に成り立つべき条件」「許される/許されない状態遷移」「計算式」「検証ルール」。どこで守られているか（or どこでも守られていない = 要注意）
4. **主要ワークフロー / ユースケース** — 代表的な業務フロー。入口（API/コマンド）→ 経由する処理 → 状態変化 → 出口
5. **境界づけられたコンテキスト** — 用語や責務が切り替わる境界。同じ語が文脈で別物を指す箇所
6. **前提・未解決の疑問** — 根拠が薄い/仕様と実装が食い違う/コードから意図が読めない箇所を**明示的にリスト化**する。ここを埋めないことが誠実さ。ユーザーに確認すべき質問もここに置く

### 3. 永続化する

- コンテキスト単位で `domain-<area>.md` に書く（小規模なら `domain-brief.md` 1枚に全軸をまとめる）
- 各ファイル冒頭に上記のメモリ frontmatter
- `MEMORY.md` に1行ポインタを追記（既に同名エントリがあれば更新）
- ファイルが大きくなりすぎる軸（用語集など）は別ファイルに分け、`[[domain-glossary]]` のように相互リンクする

### 4. 報告する

- 作成/更新したメモリファイル
- 抽出した中核概念とルールの要約
- **「前提・未解決の疑問」を筆頭に提示**し、ユーザーに確認したい点を質問する（ここでドメインエキスパートとの対話が始まる）

## ASK — エキスパートとして答える

1. **保存済みブリーフを読む** — メモリディレクトリの `domain-*.md` を読む。関連しそうなファイルを `MEMORY.md` の description から選ぶ
2. **ブリーフがなければ** — 「まだこのプロジェクトのドメインを取り込んでいない」と伝え、BUILD を提案する。ただし質問が特定の狭い範囲なら、その範囲だけ実コードを読んで即答してもよい（その場合も根拠を引用する）
3. **根拠づけて答える**:
   - すべての主張に **file:line の引用**を付ける（保存済みブリーフ経由でも、元コードを再確認できるなら確認する）
   - ブリーフに根拠がある → そのまま答える
   - ブリーフになく実コードで確認できる → 確認して答え、ブリーフに追記するか提案する
   - どこにも根拠がない → **「不明」と言う**。推測するなら「推測」と明示し、確かめる方法（読むべきファイル・聞くべき相手）を示す
4. **仕様と実装の食い違いに気づいたら**指摘する。エキスパートの価値は、両方を突き合わせて矛盾を見つけられること

**やらないこと**: 一般論のドメイン知識で答えを埋めない。このプロジェクトの仕様・実装に根拠がある事実だけを「このプロジェクトのドメイン」として語る。一般的な業界知識を使う場合は「一般論として」と区別する。

---

## REFRESH — 更新

1. 既存の `domain-*.md` を読む
2. 対象（引数で指定された範囲、なければ中核エンティティ・ドメイン層）の現在のコードを読む
3. ブリーフと現状の**差分だけ**を更新する。変わっていない記述は触らない
4. 消えた概念・変わったルールは古い記述を削除/修正する（メモリは追記ではなく整理）
5. 更新点を報告する

---

## 適用範囲の注意

- 対象言語・アーキテクチャは問わない。DDD 採用有無に関わらず「業務ルール・用語・ワークフロー」は抽出できる。ただし DDD 用語（集約・境界づけられたコンテキスト）はそのプロジェクトが該当する場合のみ使う
- CRUD 中心でドメインが薄いプロジェクトなら、無理に軸を埋めず「このプロジェクトのドメインは薄く、主な業務ルールは X のみ」と正直に書く
- コードのレビュー（不変条件が破れる箇所の指摘）が目的なら `ddd-review` / `solid-review` を使う。このスキルは**知識の抽出と応答**が役割
